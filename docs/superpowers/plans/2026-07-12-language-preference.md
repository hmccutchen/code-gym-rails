# Language Preference for Generated Problems Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let each user pick a generation language ("ruby_rails", "javascript", or "mixed") for their daily exercise sets, with "mixed" alternating single-language days, without disturbing existing Ruby/Rails-only behavior for current users.

**Architecture:** Two new columns (`users.language` = preference, `daily_exercises.language` = what a specific day was generated in) drive a `language` parameter threaded through `AiService`'s prompt-building methods. `User#language_for_today` resolves the day's actual language (pinned or alternated) once per generation; `DailyExercisesController#regenerate` reuses the stored value instead of recomputing it.

**Tech Stack:** Rails 8.0.5, PostgreSQL, RSpec.

## Global Constraints

- `language` values: exactly `"ruby_rails"` (default, unchanged current behavior), `"javascript"`, `"mixed"` — defined as a plain Ruby array constant (`User::LANGUAGES`), not a DB enum type, so a future 4th language needs no migration.
- "mixed" must keep a single day's full set (code_review, pattern, challenge) in ONE language — never split within a day, including across regenerations.
- Mixed alternation rule (exact): look at the user's most recent prior `DailyExercise` (excluding today); flip its `language` (`ruby_rails`→`javascript`, `javascript`→`ruby_rails`). If no prior exercise exists, default to `"ruby_rails"`.
- `"javascript"` ecosystem assumption: vanilla JS as primary focus, with React concepts (hooks, re-renders, controlled/uncontrolled components, state lifting) mixed in — no Node/Express backend track.
- Concept vocabulary stays closed (no AI-added concepts) — deferred as a future idea, not part of this feature.
- No changes to magic-link auth, Resend/SMTP, `/test_login`, feedback UI, regenerate-button/multi-provider work, or the email/history-page spec.
- Reuse the existing `/setup` page (`ApiKeysController`) for the settings UI — no new controller or route.
- Run `bundle exec rspec <changed files>` after each task; run the full `bundle exec rspec` after the final task.

- [ ] **Step 9: Implement `User#language_for_today`**

In `app/models/user.rb`, add this method in the `# ── Usage helpers` section or its own section right after `#recent_performance` (add a new comment section right before the closing `end` of the class):

```ruby
  # ── Language preference ────────────────────────────────────────────────────
  # Resolves the day's actual generation language. Pinned preferences return
  # themselves. "mixed" alternates by flipping the most recent PRIOR
  # exercise's language (excluding today's own row, so calling this multiple
  # times for the same day — e.g. on regenerate — stays consistent as long as
  # callers pass the result through rather than recomputing mid-day).
  def language_for_today
    return language unless language == "mixed"

    last = daily_exercises.where.not(date: Date.current).order(date: :desc).first
    return "ruby_rails" unless last

    last.language == "ruby_rails" ? "javascript" : "ruby_rails"
  end
```

        concept_text = concepts.any? ? " | concepts: #{concepts.join(', ')}" : ""
        "#{h[:date]}: #{h[:sections_answered]}/3 sections answered | #{rating_label}#{concept_text}#{feedback}"
      }.join("\n")
    end

    focus       = user.focus_areas.any? ? user.focus_areas.join(", ") : "general Rails patterns"
    label       = LANGUAGE_LABELS.fetch(language, LANGUAGE_LABELS["ruby_rails"])
    concepts    = language == "javascript" ? JS_CONCEPTS : RAILS_CONCEPTS

    <<~PROMPT

      Engineer profile:
      - Name: #{user.name}
      - Skill level: #{user.skill_level} (beginner → developing → solid → strong)
      - Priority focus areas: #{focus}

      Recent performance (last 10 sessions):
      #{history_text}

      Instructions:
      - If they've been rating exercises "too easy", increase difficulty and reduce explanation in the reference.
      - If they've been rating "too hard" or skipping sections, simplify and add more scaffolding.
      - Prioritize focus areas they've missed or rated hard recently.
      - The code_review snippet must be realistic #{label} code — not toy examples.
      - The challenge starter_code should give enough scaffold to get started without giving away the answer.
      - Rotate between topics across sessions — avoid the same pattern two days in a row.
      - Each teaching_note must point toward how to think about the problem or the right question to ask — one or two sentences, never the full answer.
      - Choose each section's concept from this fixed vocabulary, exactly one per section: #{concepts.join(", ")}
      - Mastery loop: for any concept whose most recent rating was "too hard", reintroduce that concept in this set with a different code example and framing — same underlying concept, never a repeat of the same snippet. Keep reintroducing it in every subsequent set until the user rates a set containing it "right level" or "too easy"; that rating is the mastery signal that ends reinforcement for that concept.
