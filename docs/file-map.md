# File Map

What each listed file does.

- `app/models/track_change.rb` — `TrackChange`: which per-kind targets a track change clears, the one statement of the rule; pure.
- `app/forms/profile_update.rb` — `ProfileUpdate`: `PATCH /profile`'s form. Checks the posted shape, runs the stale-page and track-choice checks under the user-row lock, saves through `LevelChange` in one transaction, and returns an `Outcome` the controller maps to JSON; which values a field allows stays with `User`'s validators.
- `app/models/level_change.rb` — `LevelChange`: one profile save's level bookkeeping, in the order `ProfileUpdate` calls it: clear the targets a track change covers, record cutoffs for kinds whose rung moved, then write the applied event rows.
- `app/models/level_suggestion.rb` — pure proposal rules: one-rung moves up and back along junior, mid-level and senior, each kind judged on its own results, and the evidence counts a card and an event row show.
- `app/models/level_suggestion/evidence.rb` — bounded, preloaded reviewed-response history projected into stamped, answered, rubric-graded results.
- `app/models/reviewed_section_results.rb` — `ReviewedSectionResults`: which sections of one submitted, reviewed response count as evidence of work at a rung, optionally only under the current rubric. Pure over the response it is given; shared by `LevelSuggestion::Evidence` and `CompetencyGate::Evidence`.
- `app/models/competency_gate.rb` — `CompetencyGate`: the pure fold that earns a day's size from reviewed days, with the brake. `DailyPlan.size_for` calls it once per plan.
- `app/models/day_size.rb` — `DaySize`: the day's planned count and its reason, from the Daily sections setting, the completion count and the gate's `Plan`. Pure; its `Decision` also answers whether the brake is on, for the coverage exception, and what the `[set_size]` line logs.
- `app/models/size_forecast.rb` — `SizeForecast`: whether tomorrow's Automatic set will be larger, or smaller because of the brake, than today's planned one, for the submitted dashboard's size lines.
- `app/models/competency_gate/evidence.rb` — the gate's only query: every rubric-stamped reviewed day, oldest first, in batches, as `CompetencyGate::Day` values, each carrying the pair its row was planned with.
- `app/controllers/welcome_controller.rb` — the first-run experience question; choices save through `ProfileUpdate`.
- `app/controllers/level_suggestion_dismissals_controller.rb` — records Not now and removed-kind cutoffs for the current user under the user-row lock, refusing a stale shown step with a 409, with a `dismissed` or `removed` event row for each kind whose cutoff moves forward.
- `app/models/level_suggestion_step.rb` — `LevelSuggestionStep`: one move a card or Setup showed, and the boundary check on the steps they post.
- `app/models/level_suggestion_event.rb` — `LevelSuggestionEvent`: one row per answer to a level suggestion (`applied`, `dismissed`, `removed`) with the evidence counts behind it; builds applied rows by rung, with `skill_level_edit` for a kind the skill level moved, from the state `LevelChange` passes in from before the save.
- `app/controllers/daily_kinds_controller.rb` — `PATCH /daily_kinds/:place`: maps a `DailyKindSwap` outcome to JSON, the reply, new pair and every daily card's re-rendered panel on a save, a 409 with the current pair and those panels for a stale page (panels only for the generation the page posts as `draft_scope`, else a `set_changed` sentence), and a 422 naming the reason for every other refusal
- `app/controllers/level_suggestion_answers_controller.rb` — counts an answered proposal, which decides whether the next one applies in place or links to Setup.
- `app/views/dashboard/_regenerate_row.html.erb` — Today's "Generate new set" and "Start over" controls with the hint that replaces them, rendered once in the side column
- `app/views/dashboard/_level_suggestion.html.erb` — submitted-day proposal with counts from the evidence, a removable list when several kinds share a destination, and in-place Apply/Not now saves.
- `app/views/api_keys/_daily_sections.html.erb` — Setup's Daily sections control: the count radios, a hidden chooser for each count that asks which daily section to keep or which kinds to add, and the hint; driven by `daily_sections_controller`.
- `app/views/api_keys/_level_suggestions_switch.html.erb` — the "Suggest level changes" switch at the top of Setup's Exercise mix, for every account; its `save-switch` controller takes focus when the card's link asks.
- `script/prepare_junior_ladders.rb` (+ `script/junior_ladder_preparation.rb`) — operator coverage report; explicit `--run` queues shared-reference refreshes using the operator's key.
- `spec/requests/existing_account_pages_spec.rb` — exact pre-track Dashboard, Setup, Account, History, Progress and Learn snapshots. Propshaft digests in `/assets/` paths become `-DIGEST` before comparing, so editing a controller or an image does not move them; the layout's inline CSS and the `?v=` query on public icons still do. `UPDATE_PAGE_SNAPSHOTS=1` intentionally rewrites fixtures; never use it to conceal a learning-track regression.
- `spec/prompts/duck_prompt_characterization_spec.rb` — the duck's exact system, history, prompt and request settings for a first turn and a turn with history, and that string-keyed stored turns send the same bytes (`spec/fixtures/duck_prompt_snapshots/`), kept apart from the generation snapshots, whose spec fails on any file it did not write. `UPDATE_PROMPT_SNAPSHOTS=1` rewrites them; only a deliberate duck prompt change should.
- `app/models/duck_thread.rb` — `DuckThread`: each exercise's stored duck threads, keyed by section; the one authority for a section's turns, user-turn count and version, appending under the exercise lock and a version check, and counting clears. Read by nothing in generation, review, the judges, mastery or planning.
- `app/jobs/sweep_duck_threads_job.rb` — daily: deletes duck threads whose exercise is older than `DuckThread::KEPT_FOR` (365 days).
- `spec/services/duck_thread_isolation_spec.rb` — fails if generation, review, the judges, mastery or planning code reads `DuckThread`.
- `app/clients/ai_service.rb` — provider-agnostic base: provider orchestration through the `#call(request)` template, the `AiService::Request` value each call carries and `.request_for`, which builds it from the purpose's row in `CallProfiles::BY_PURPOSE`, JSON parsing, usage logging. The generation prompt is rendered by `GenerationPrompt`, which this class builds through its private `#generation_prompt` factory and hands to `ExerciseDraft` as a callable, with `#generate_problem_set` for the call and the parse; `#annotate_retention_concept` stays here as that prompt's retention callable because `RealSource` lists it as a curated excerpt. Owns `#assess_difficulty`'s deliberately narrow signature; `DailyResponse.usable_difficulty` owns what a storable/renderable assessment is, and is applied on write and again on read. Also owns the two-stage entry point: `#generate_judged_exercise` drafts through `ExerciseDraft`, then hands the draft to `JudgedGeneration`
- `app/prompts/generation_prompt.rb` — `GenerationPrompt`: `.system_prompt` renders the generation system prompt from the language's coach and focus; an instance renders the generation prompt and its JSON schema from the plan, history, difficulty and ladders as whole values, `only:` and `fixed_concept:` narrowing a retry to one kind and `retry_cause:` saying why its section was turned down; reads no database, clock or random state. Includes `GenerationPrompt::ConceptGuidance`
- `app/prompts/generation_prompt/retry_reasons.rb` — `GenerationPrompt::RetryReasons`: the one table of fixed lines a retry prompt uses to say why the section it replaces was turned down, keyed by the judge's principle or a kind's refusal code; `spec/fixtures/retry_reason_snapshots/` holds one snapshot per line
- `app/prompts/generation_prompt/concept_guidance.rb` — `GenerationPrompt::ConceptGuidance`: the one prompt line per concept group, each named from its `ConceptVocabulary` constant and stated once for every section
- `app/prompts/prompt_standards.rb` — `PromptStandards`: prompt text several families share, `PLAIN_LANGUAGE_STANDARD`, `.explain_differently_standard` and `.prior_framings`
- `app/prompts/section_context.rb` — `SectionContext.render`: one section described for a prompt (the duck and the difficulty assessment), field by field so no answer key reaches it
- `app/prompts/pseudocode_prompt.rb` — `PseudocodePrompt`: the pseudocode critique and translation prompts; `.critique` and `.translate` return the `system:` and `prompt:` for `AiService.request_for`, so the text has one home
- `app/prompts/concept_reference_prompt.rb` — `ConceptReferencePrompt`: the concept reference prompt and its reframe; `.generate` and `.reframe` return the `system:` and `prompt:` for `AiService.request_for`
- `app/prompts/recognition_guide_prompt.rb` — `RecognitionGuidePrompt`: the recognition guide prompt; `.generate` takes the group and its subject and returns the `system:` and `prompt:` for `AiService.request_for`
- `app/prompts/explain_differently_prompt.rb` — `ExplainDifferentlyPrompt`: the prompt that re-explains a reviewed section's missed points; `.generate` takes the question, answer, missed points and earlier framings as values and returns the `system:` and `prompt:` for `AiService.request_for`
- `app/prompts/follow_up_prompt.rb` — `FollowUpPrompt`: the prompt that answers a follow-up question about a reviewed section; `.generate` returns the `system:`, `history:` and `prompt:` for `AiService.request_for`
- `app/prompts/duck_prompt.rb` — `DuckPrompt`: the duck's system prompt and the canned explain request its button sends; `.generate` takes one section's data, the new message and the thread, and returns the `system:`, `history:` and `prompt:` for `AiService.request_for`
- `app/prompts/difficulty_prompt.rb` — `DifficultyPrompt`: the post-review difficulty assessment's prompt and its level guidance; `.generate` takes the coach and the sections and returns the `system:` and `prompt:` for `AiService.request_for`
- `app/prompts/section_judge_prompt.rb` — `SectionJudgePrompt`: the prompt for the judge that checks one generated section; `.visible` strips answer keys, server stamps and the kind's `.judge_hidden_fields`, and `.generate` renders that, prints the kind's `.judge_attachment` after the section, and returns the `system:`, `prompt:` and `response_schema:` for `AiService.request_for`
- `app/prompts/review_prose_judge_prompt.rb` — `ReviewProseJudgePrompt`: the prompt for the pass that rewords a graded review's prose; `.generate` takes the kind, the coach and the review's prose and returns the `system:`, `prompt:` and `response_schema:` for `AiService.request_for`
- `app/prompts/review_prompt.rb` — `ReviewPrompt`: the two-stage review's text and `RATING_RUBRIC`; `.day_system` renders the day-level system prompt from each section's values, `.for_section` chooses a section's prompt from whether it was answered, `.section_prompt` is the per-section grading prompt at the rung it is handed, and `.walkthrough_prompt` the ungraded walkthrough for an unanswered section
- `app/services/generation_diagnostics.rb` — `GenerationDiagnostics`: the log lines a generation writes (`[set_size]`, `[unusable_section]`, `[planted_key]`, `[retention]`, `[shared_concept]`, `[coverage]`, `[difficulty_diagnostics]`), with answer-key fields stripped from the delivered set through `ExerciseSection.without_answer_keys`; writes nothing but logs
- `app/prompts/generation_prompt/difficulty_guidance.rb` — `GenerationPrompt::DifficultyGuidance.render`: the difficulty block, every planned kind at its rung with ladder rungs and lock lines; the prompt and `GenerationDiagnostics#kind_difficulty` both call it, so the logged character count is the text sent
- `spec/support/generation_prompt_helpers.rb` — `render_generation_prompt`, `generation_schema` and `plan_for`: render a prompt or schema from a `DailyPlan::Result` built on legacy test defaults (`PLAN_DEFAULTS`), with the real `AiService#annotate_retention_concept` bound from a service that can never open a connection
- `app/services/judged_generation.rb` — `JudgedGeneration`: the two-stage path after the draft. Fans the judge out a section at a time, retries a rejection, or a planned section ingest refused, up to the plan's `judge_retries` for that kind (twice for a daily kind, once otherwise) with its concept fixed, drops a rejected last retry, re-judges a design comparison's edits, and hands the final set to its `finish` callable (`ExerciseDraft.finish`, from `AiService`). It reaches the provider only through `JudgedGeneration::Provider` (`judge_section`, and `retry_section` taking the draft, kind and concept, as callables built fresh per call), so its specs need no provider subclass. `JudgedGeneration::UnhostedConcepts` names the planned concepts a drop left without a host. Every judge pass on a kind the judge solves blind becomes a `JudgedGeneration::Solve`, kept per kind by `JudgedGeneration::SolveChain`, which decides `shipped` and `never_shown_reason` from what the run kept; the solves come back on `AiService::JudgedSet#solves`, never inside `outcomes`
- `app/models/generation_ladders.rb` — `GenerationLadders.for`: loads each requested kind's difficulty-ladder rungs from `ConceptReference`, at that kind's rung, for the vocabulary the day's `code_review` mode allows, merged by level and each truncated to `ConceptReference::MAX_LADDER_RUNG_LENGTH`. `ExerciseDraft` reads it for the draft and the single-section retry, and `GenerationPrompt` renders the result
- `app/services/exercise_draft.rb` — `ExerciseDraft`: drafts the day's set (plan, history, difficulty, ladders, prompt, one provider call, ingest) into an `ExerciseDraft::Draft` that carries its user and language, retries one section from that draft with its concept fixed, and finishes a set by recording suggested concepts and the generation diagnostics. It reaches the provider only through `ExerciseDraft::Provider` (`prompt`, `generate` and `record_suggestion`, built by `AiService#exercise_draft_provider`), so its specs need no provider subclass
- `app/models/generation_deadline.rb` — `GenerationDeadline`: refuses a provider call whose worst case (`AiService::Request#worst_case_seconds`) would end after the deadline, raising `ProviderError::DeadlineError`. `AiService#call_and_log` checks it first, after the request is built; `#leaving` keeps time back so a retry reserves its re-judge. `NONE` is the no-deadline default
- `app/models/problem_set_ingest.rb` — the generation boundary: holds concepts to their closed vocabulary, bounds scaffolds and diagrams, runs each resolved section's own `.reject_unusable!` check, leaving a refused section out and reporting it on `Result#unusable_sections`, notes each keyed section's answer-key outcome on `Result#key_notes`, calls each resolved section's `.arrange!` (the Parsons scramble, the design comparison's A/B order), and logs a section the day never asked for. Writes nothing to the database — off-vocabulary concepts come back on the `Result` for `ExerciseDraft.finish` to record, so a rejected set structurally cannot leave a `SuggestedConcept` row behind, and its specs need no database. Not side-effect free, though: `warn_unrequested_sections!` logs.
- `app/models/planted_key.rb` — `PlantedKey`: bounds the answer key the four newer discovery kinds plant (text, lists, required fields), stores or deletes it, and finds a key's backticked quotes the shown code or plan doesn't contain. Pure
- `app/models/key_quote.rb` — `KeyQuote`: the one matcher for provider-quoted text against formatted code; normalizes whitespace, a trailing comma and, on JavaScript, Prettier's rewrites, finds the one whole line or wrapped run a quote equals (`.line`), and the range of lines a quote spans (`.find`). Pure
- `app/models/planted_key/kind.rb` — `PlantedKey::Kind`: extended by a section kind that plants a key; holds `.planted_key?`, the shared quote check, and the hooks the kind must answer (its key shape, which key text quotes, the fields it is checked against)
- `app/models/daily_plan.rb` — the day's plan (third section, reinforcement, the shared concept, retention checks and the ones left waiting, the coverage addition, `code_review` mode and the real-source excerpt grounding it, if any), decided before any provider is contacted; pure decision, no prompt or HTTP

- `app/models/daily_kind_swap/picker.rb` — `DailyKindSwap::Picker`: what one daily card's swap control shows. `.for_day` keys a picker by each delivered daily card's kind; each option's state and note come from `DailyKindSwap#refusal`, and a refusal of the place's own kind (an ended trial) closes the picker

- `app/models/daily_kind_swap_event.rb` — `DailyKindSwapEvent`: one row per saved swap in `daily_kind_swaps` (place, both kinds, the outgoing section's state in today's set, today's planned size, the size setting)
- `app/models/exercise_section.rb` (+ `app/models/exercise_section/`) — the registry of section kinds (code_review, design_comparison, pattern, challenge, architecture, security_review, parsons_problem, plan_review, ambiguity_hunt, pseudocode_to_code); one class per kind answers which are in the default daily pair (`.default_daily?`, which `DailyKinds::DEFAULT` reads), which slots a daily pair gives a day (`.layout(daily:)`, `.optional_slots(daily:)`), which are thirds, which are fourths, which vocabulary they draw from and how it narrows that list for generation (`.narrow_vocabulary`, given an optional rung), which fields are answer key (`.answer_key_fields`), what the provider boundary refuses (`.reject_unusable!`, each refusal named by a code in `.refusal_codes`), any extra judge instructions (`.judge_guidance`), how a resolved section is arranged after it is accepted (`.arrange!`), whether the judge solves it blind (`.judge_solve_options`, `.keyed_solve`, `.solve_matches_key?`), which show improved code, which scaffold their answer, and — via `.schema_fragment` / `.generation_guidance` — what the generation prompt says about them. `AiService` assembles those fragments, and each language's prompt wording is `LanguagePrompts`; it no longer branches on section keys — or on kind identity — to build them. `.generation_guidance` takes a uniform context (`vocabulary:, label:, mode:, artifact:, test_framework:, source:, rung:, alongside:`, the last being the other kinds requested with it, not the day's kinds) that every kind receives and each reads only its own part of; kinds that read none of the optional values absorb them with `**`. Adding a kind means adding a class here, not editing `AiService`.
- `app/models/code_format.rb` (+ `app/models/code_format/ruby.rb`, `app/clients/code_format/javascript.rb`) — `CodeFormat`: re-indents a batch of exercise code in the day's language, RuboCop's Layout cops for Ruby and Prettier (through Node, so an adapter in `app/clients`) for JavaScript, handing back what it cannot format unchanged
