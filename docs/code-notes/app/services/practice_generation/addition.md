# PracticeGeneration::Addition

Reuses the parent's capture validation and judge-solve persistence. Capture
and commit use the addition service's owner-first lock wrapper. A requested
kind travels in the immutable context, so the ordinary provider pipeline asks
for exactly that kind without a separate generation API.

Append merges one key rather than calling replacement. It does not destroy
response data or alter generated_at. It writes only the locked target
exercise, never an older row that supplied scheduling context. A note-free
target receives the generated continuation, with its original active keys
and no reconstructed initial assignments. The captured predecessor already
supplies prior service to that generated continuation.

Only the touched kind's continuation service merges into an existing
format-3 target note; a changed predecessor rejects the candidate. Legacy
target notes use the current translation rules. The initial schedule
envelope remains separate from added-kind service. No separate additions
ledger is written because no reader uses it; existing unknown plan metadata
is preserved.

See docs/decisions/on-demand-exercise-additions.md for lifecycle and deployment.
