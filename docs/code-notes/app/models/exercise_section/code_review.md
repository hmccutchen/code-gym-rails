# app/models/exercise_section/code_review.rb

## `MAX_SNIPPET_LINES`

The prompt asks for a snippet of about 10 to 15 lines, but until issue #599 nothing checked the reply, and a long snippet costs the most on a phone, where every extra line is more scrolling before the question.

The cap is `RealSource::MAX_LINES` (40) rather than a tighter number. A grounded day asks for a modified copy of a curated excerpt that keeps its shape, and an excerpt can be up to 40 lines, so a lower cap would refuse legitimate grounded sections. A spec runs every curated excerpt through the formatter and the check to hold that. A tighter cap for the toy modes would need a measurement of what providers actually return first. `SecurityReview::MAX_SNIPPET_LINES` reads this constant (#604), so changing it for grounding reasons also moves security_review's cap and its retry line.

Lines are counted after `ProblemSetIngest#format_code!`, so the cap measures the code as shown, and blank lines don't count, the same rule design comparison's `MAX_PIECE_LINES` uses (`ExerciseSection.shown_lines`).

A snippet over the cap is refused, never cut, since cutting code could cut out the planted flaw. `code_review` is a daily kind, so on a judged day a refusal gets up to two retries with its concept fixed before the section is dropped; a weekend set drops it straight away. The refusal message carries the line count and none of the code. A missing or blank snippet is refused the same way.

## Two shapes: one snippet, or two to three files

A `code_review` section comes in one of two shapes. The single-file shape is the `snippet` described above. The multi-file shape replaces it with up to three files in flat fields, `file_N_path`, `file_N_code` and `file_N_changed` for N from 1 to 3, plus the server's `file_N_changed_lines`, so the problem can sit in how files of one change fit together. A multi-file section has no `snippet` and no diagram: two or three files already show the structure, and a diagram of how they connect would point at the flaw, so `.arrange!` deletes one a provider sends.

`.files(section)` is the one reader of the `file_N_*` fields. It returns a `CodeReview::File` for each file with both a path and code, in order, and an empty list for a single-file section, so the page and the review context read files the same way.

`.key_context_fields` lists every file slot's code field (`FILE_CODE_FIELDS`) beside `snippet` and `current_schema`, so ingest's quote check reads a multi-file key's quotes against its files, and the key sheet shows them. A single-file section has no file fields, so its check and its sheet entry are unchanged.

Ingest tells `.reject_unusable!` the file range the day planned (`file_range:`, from `ProblemSetIngest`'s `code_review_files:`). A range whose top is 1 runs exactly the snippet checks above. Any other range runs the multi-file checks, in this order: an incomplete file or a field of the wrong type (`file_incomplete`) first, so half a third file reads as incomplete rather than as a wrong count; then a `snippet` or a file count outside the range (`file_count_wrong`); then length (`file_too_long`); then paths (`path_invalid`); then changed lines (`changed_lines_unresolved`). A passing section loses every field of a file slot that has neither path nor code (`FILE_FIELDS`), so a stray `file_3_changed` reaches nothing.

## Caps on files

Each file may show at most `MAX_FILE_LINES` (15) lines, about a screen and a half on a phone, and all files together at most `MAX_SNIPPET_LINES`, the same 40 a single snippet may show. Lines count the way the snippet cap counts them, with `ExerciseSection.shown_lines` after formatting, so blank lines don't count and there is one way to count. A path may run to `MAX_PATH_LENGTH` (120) characters, may hold no line break or other control character, and no two files may share one. Prompts print a path as plain text on its own `File:` line, so a line break in one would read as a line of its own, such as a forged `Changed lines:` (#633). A file past a cap is refused, never cut, for the same reason a long snippet is: cutting code could cut out the flaw. The refusal messages carry counts and numbers only, never code, a path or a quoted line.

## Why changed lines are quoted, and resolved after formatting

The provider can't count lines reliably, and formatting moves them anyway: RuboCop re-indents Ruby and Prettier rewraps JavaScript. So the provider quotes each changed line's text, and `.reject_unusable!`, which ingest runs after `format_code!`, resolves each quote against the formatted code with `KeyQuote.line`, by whole-line equality with whitespace ignored. A quote matching exactly one line resolves; on JavaScript a quote can also match one run of lines Prettier wrapped, and every line of the run is marked. A quote matching several lines, such as `end`, or none is dropped instead of guessed. The sorted, unique 1-based line numbers go into `file_N_changed_lines`, and the quotes stay in `file_N_changed`, so the check can run again on a stored or edited section and reach the same numbers (#623). Before #623 the numbers replaced the quotes, and a second run refused the section as `file_incomplete`, since the quote field then held numbers. Keeping the two apart also means a provider can't skip the match by sending numbers: numbers in `file_N_changed` are refused as the wrong type, and every run writes `file_N_changed_lines` afresh for each file with code, so a provider's copy never survives. `.files` reads only `file_N_changed_lines`. A section where no file keeps a changed line is refused, since the page would have nothing to mark as the change. Since the match depends on the language's rules, a multi-file range raises `ArgumentError` when no `language:` is given, rather than guess one; ingest always passes the set's language.

## A single-file range drops every file field

On a range whose top is 1, `.reject_unusable!` also deletes every `file_N_*` field once the snippet passes. `.files` decides the shape for the page, the review context and `.arrange!`, so a stray file field on a single-file day would otherwise turn it into a multi-file section with a snippet nobody shows.

## How files reach a prompt

`CodeReview::File#prompt_text` is the one way a file reads in a prompt: its path, its changed line numbers (or "none") and its code with every line numbered (`4 | def total`), blank lines included and the numbers right-aligned from ten lines. Each line keeps its text exactly, trailing whitespace included, since a heredoc or template literal can carry it in its value and the page shows it; only an empty line drops the space after the bar. The numbers count physical lines the way `KeyQuote.line` does, so "Changed lines: 4" points at the line marked 4 and a model never counts lines to find it (#630). The page numbers each file's lines in a gutter beside the code, counting the same way, so a review or the duck can cite "line 4" and the engineer sees line 4 (#634). `.files_context` puts `NUMBERED_FILES_NOTE` above the files: it says the page numbers lines the same way and that the `N | ` prefix is not code, so the grader never copies it into `improved_code`. `.review_context` (in place of the `Code snippet:` line) and `SectionContext` (for the duck and the difficulty assessment) use `.files_context`. The judge (`.judge_attachment`) gets the same numbered files without the note, since it writes no code and its own heading says what the numbers mean. None of them can describe files differently. A single-file section has no files, so both render as before. Neither reads `answer_key`.

## `.file_range`: the one place the file count is decided

`.file_range(files:, rung:)` turns the day's files roll (`DailyPlan::Result#code_review_files`) and the rung `code_review` is pitched at into the range of files the day asks for. A `:single` day is `1..1` at every rung. A `:multi` day is `1..1` at `junior`, `2..2` at `mid_level` and `2..3` at `senior` and `principal_engineer`; an unknown or missing rung reads as `junior`. The two top rungs share a count and differ in how subtle the problem is, which keeps the 40-line total in reach. `MULTI_FILE_RANGES` is keyed by every `KindDifficulty::LEVELS` entry, and a spec holds both that and its widest range to `FILE_SLOTS`.

`.day_file_range(plan:, difficulty:, skill_level:)` reads the rung with `KindDifficulty#rung_for`, the same rung the generation prompt's difficulty block and `pitched_at` use. `GenerationPrompt` calls it to shape the prompt and `ExerciseDraft` calls it to hold ingest to the same range, on the draft and on a retry, so the prompt and the boundary check can't disagree. A retry keeps its draft's plan and difficulty, so it gets the same range. Easing changes a concept's tier, never the rung, so an eased section keeps its range too.

## How the prompt asks for files

`GenerationPrompt` passes `file_range:` (and the language's `code_style:` from `LanguagePrompts`) to every kind's `.generation_guidance` and `.schema_fragment`, and every other kind absorbs them with `**`, so the prompt needs no branch on kind. On a range whose top is 1 both methods render exactly what they rendered before files existed; the prompt snapshots hold that byte for byte.

On a wider range `CodeReview::MultiFile` writes both. The guidance replaces the mode's snippet line with a line for that mode's files (a change and its caller, a change and its test, a schema change and the code that depends on it), states the rung's subtlety, gives the line caps, asks that every change add or edit at least one line and that each changed line appear only once in its file (so `KeyQuote.line` can resolve it), and on JavaScript asks for Prettier's style, whose rewrites `KeyQuote` undoes. It keeps the vocabulary line word for word. Its hidden `answer_key` line comes from `CodeReview.hidden_key_line`, the builder the single-file line uses, so the two can differ only in what they name: the multi-file line leaves out `diagram`, which the section doesn't have, and says the engineer reads the files rather than the snippet. When the vocabulary it is given offers `authorization`, it also adds that such a flaw here is a broken contract between files, so it stays out of `security_review`'s way; a vocabulary without it, such as JavaScript's or a schema review's, gets no such line. The fragment drops `snippet` and `diagram`, asks for `file_1` and `file_2`, offers `file_3` only when the range allows three, and keeps the same `answer_key` object (`ANSWER_KEY_SCHEMA`, shared with the single-file fragment). The key's `files` and `evidence` come with keyed grading, later.

A `RealSource` day is always single-file, so the multi-file guidance never meets an excerpt's own instruction.

## The judge

Launch A gives the judge no paragraph about files: `code_review` keeps the base `.judge_guidance`, which is nil, so the judge prompt is unchanged. The paragraph that asks the judge to solve a multi-file section and reject one that a single file explains arrives with launch B, when real days first ask for files (`docs/decisions/multi-file-code-review.md`). The blind solve stays off for `code_review`.

The judge sees each file through `File#prompt_text`, after the section's JSON: `.judge_hidden_fields` names every `file_N_*` field, which `SectionJudgePrompt` leaves out of the JSON, and `.judge_attachment` returns the numbered files under a line saying "Changed lines" are the lines the page marks (#630). So the judge sees the changed line numbers the page marks and never the provider's quotes (#625): a quote that matched no line, or several, marks nothing on the page, so showing it would describe a change the engineer never sees. Launch B's paragraph should say "Changed lines" when it tells the judge never to change the changed lines. `section_judge_prompt_spec` snapshots the prompt for an ingested multi-file section.
